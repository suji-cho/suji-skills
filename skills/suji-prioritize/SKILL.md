# suji-prioritize

"다 중요하고 급해"를 풀기 위한 3-질문 프레임워크.
알아서 정하지 않는다. 질문을 통해 사용자가 직접 판단하도록 돕는다.

**scope: work (개인 프로젝트는 사용자 요청 시만 포함)**

## When to use

- "우선순위 정하자", "뭐부터 해야 하지", "다 급해"
- `/suji-prioritize`
- 데일리 작성(`/suji-work-minute`) 후 우선순위 컬럼이 비어 있을 때

## 파이프라인 위치

```
/suji-work-minute (데일리 노트 생성 + 할일 수집)
    ↓
/suji-prioritize (우선순위 가이드 → P0~P3 배정)
    ↓
/suji-work-minute close (마감 정리)
    ↓
/suji-report (성과 리포트 소재)
```

## 설정

```
DAILY_BASE=~/Workspace/work/hand-ons/work_minutes/2026/daily_task
DAILY_PATH=$DAILY_BASE/YYYY Mon
MONTHLY_TODO_PATH=~/Workspace/work/hand-ons/work_minutes/2026/monthly_task
PROJECT_TODO_PATH=~/Workspace/work/project_todo
```

## 커맨드

```
/suji-prioritize            → 오늘 데일리 기준 전체 우선순위 가이드
/suji-prioritize weekly     → 이번 주 단위로 우선순위 정리
```

## P 레벨 기준

P 레벨은 사용자가 정한다. 아래는 판단을 돕기 위한 기준이며, 최종 결정은 항상 사용자 몫이다.

### 판단 순서 (위가 더 강한 기준)

1. **내 평가·커리어에 직결되는가?** — 본인 평가 점수에 영향 주는 일이 외부 기한보다 우선할 수 있다
2. **누가 기다리는가?** — 외부(팀장·파트너·고객) > 내부(내 다른 작업) > 나만
3. **기한이 있는가?** — 컨펌 체인이 있으면 단계 수 × 1일로 역산
4. **뭘 풀어주는가?** — 의존성 체인의 첫 노드일수록 우선
5. **금방 끝나는가?** — 30분 이내면 빈 시간에 치울 후보

### P 레벨 정의

| 레벨 | 의미 | 전형적 조건 |
|------|------|-----------|
| P0 | 오늘~이번 주 필수 | 평가 직결, 컨펌 체인 역산 "오늘", 하드 데드라인 |
| P1 | 이번 주~다음 주 중요 | 외부 대기, 중요도 높음, 체인 첫 노드 |
| P2 | 해야 하지만 덜 급함 | 이번 주 하긴 해야 하는데 P0·P1보다 후순위 |
| P3 | 급하진 않지만 해야 할 일 | 기한/대기자 없음, P0~P2가 다 찬 뒤 배치 |

레벨을 제안할 때는 반드시 근거를 함께 말한다:
- "P3입니다" ✗
- "P0~P2가 다 찼고, 기한이나 대기자가 없으니 P3으로 보이는데 어떠세요?" ✓

## 워크플로우

### Step 1: 태스크 수집

아래 경로에서 현재 열린 태스크를 수집한다:
- 오늘 데일리 노트 (`DAILY_PATH/yyyymmdd.md`) — 작업공수 비어있는 행
- 최신 월간 TODO (`MONTHLY_TODO_PATH/YYYY Mon TODO.md`) — 미완료 항목
- 프로젝트 카드 (`PROJECT_TODO_PATH/*.md`, done/ 제외) — 미완료 항목
- 메모리의 활성 프로젝트 — project_*.md

미완료 항목만 추출. 중복 제거 후 목록을 만든다.

수집 시 주의:
- **내 업무가 아닌 것은 제외한다.** 개발자 업무, 상대방이 보내야 할 것 등. 애매하면 "이건 내가 할 일인가요?" 질문.
- **"요청 오면 대응" 성격은 대기 항목으로 분리한다.** 능동적 행동이 필요한 것만 목록에 남긴다.
- **항목 내용이 불분명하면 빼지 않는다.** 사용자에게 재정의를 요청한다.

### Step 2: 질문 1 — "이걸 안 하면 누가 막히나?"

수집된 태스크를 3단계로 분류하여 보여준다:

| 레벨 | 기준 | 예시 |
|------|------|------|
| 🔴 외부 대기 | 팀장·파트너·고객이 내 아웃풋을 기다림 | 보고서, 보도자료, 리뷰 요청 |
| 🟡 내부 대기 | 내 다른 작업이 블록됨 | 인프라 세팅, 의존성 첫 노드 |
| 🟢 나만 대기 | 나만 기다리는 일 | 자동화 개선, 도구 정비 |

추가 확인:
- "이 중에 본인 평가에 직접 영향 주는 게 있나요?"
- "이 목록에 없는데 머릿속에 있는 항목이 있나요?"

> 사용자에게 확인: "이 분류가 맞나요? 옮기거나 뺄 항목이 있으면 알려주세요."

### Step 3: 질문 2 — "이걸 하면 뭐가 풀리나?"

🔴·🟡 그룹 내에서 의존성 체인의 첫 노드를 식별한다:
- `depends` frontmatter가 있으면 DAG 기준으로 판단
- 없으면 사용자에게 질문: "이 태스크가 끝나면 바로 시작할 수 있는 다음 일이 있나요?"
- 체인 길이가 긴 첫 노드일수록 우선

기한이 있는 항목은 역산한다:
- 컨펌 체인이 있으면 (팀장→실장→CTO→홍보팀 등) 단계 수 × 1일로 계산
- 역산 결과 "오늘 안에 해야 하는 것"이 나오면 최우선 후보

> 사용자에게 확인: "이 순서가 맞나요?"

### Step 4: 질문 3 — "30분이면 끝나나?"

전체 목록에서 30분 이내 완료 가능한 항목을 별도 표시한다.
단, P0 항목보다 앞에 배치하지 않는다.
"빈 시간에 치울 것" 후보로만 제시.

> 사용자에게 질문: "이 중에 오늘 빈 시간에 치울 것이 있나요?"

### Step 5: 사용자와 P 레벨 확정

**하나씩 확인한다.** 일괄 배정하지 않는다.

1. 가장 급하다고 한 항목부터 시작: "이건 P0 맞나요?"
2. 사용자가 순서를 말하면 그대로 따른다
3. 나머지 항목은 "그 다음은요?" 로 이어간다
4. 사용자가 "나머지는 나중에" 하면 멈춘다
5. 레벨 간 경계가 애매하면 사용자에게 물어본다

### Step 6: 데일리 반영

확정된 P 레벨을 오늘 데일리 노트의 `우선순위` 컬럼에 업데이트한다.
- 사용자가 확정하지 않은 항목은 비워둔다
- 항목명이 변경된 것(재정의된 것)도 함께 반영한다
- 새로 추가된 항목이 있으면 테이블에 행을 추가한다

## 규칙

- **판단하지 않는다.** 질문하고, 분류하고, 제안한다. 최종 결정은 사용자 몫.
- **사용자가 분류를 바꾸면 즉시 반영한다.** 이유를 묻지 않는다.
- **"다 급해"라고 하면** 질문 1부터 다시 시작한다.
- **개인 프로젝트는 기본 제외.** 사용자가 넣자고 하면 포함.
- **컨펌 체인이 있으면 반드시 역산한다.** 몇 단계인지, 순서가 어떻게 되는지 확인.
- **항목 내용이 불분명하면 빼지 않는다.** 사용자에게 재정의를 요청한다.
- **일괄 배정하지 않는다.** 하나씩 사용자와 확인하면서 진행한다.
