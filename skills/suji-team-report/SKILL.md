# suji-team-report

**팀에 공유하는 주간 리포트**를 만든다. 두 갈래를 각각 뽑아 한 벌로 합친다.

- **1부 제품 문의 대응 현황** — Gmail `OSS/BIZ contact` 라벨 확인 → 신규·회신 반영 → criteria v1.3 점수 산정 → 대기일 재계산
- **2부 한일·할일** — 데일리 노트를 보고·공유용 압축 리스트로

**scope: work only**

## 커맨드

```
/suji-team-report              → 두 파트 모두 + 교차 반영 후 합본 출력
/suji-team-report [붙여넣기]    → 직전 주 리포트를 기준으로 갱신
/suji-team-report biz          → 1부 제품 문의 현황만
/suji-team-report tasks        → 2부 한일·할일만
```

## 전제

- **직전 주 리포트가 입력(SoT).** 붙여넣은 리포트가 기준. 임의로 라벨·그룹·비즈니스 흐름을 바꾸지 않는다 ([[feedback_no_label_or_flow_rename]])
- **점수 기준**: `~/Workspace/work/outputs/odl_business/governance/criteria/v1.3_20260601/` (criteria v1.3)
- **룰북(참고용)**: `~/Workspace/work/outputs/odl_business/contacts/biz_contact_tracker.md` (스키마 v2.2, 양식이 다르므로 자동으로 덮어쓰지 않음)
- **Gmail 라벨**: `OSS/BIZ contact` (ID는 매번 list_email_labels로 확인)
- **데일리 노트**: `~/Workspace/work/hand-ons/work_minutes/2026/daily_task/YYYY Mon/yyyymmdd.md`

# 1부. 제품 문의 대응 현황

## Step 1. 직전 리스트 확보

- 사용자가 직전 리포트를 붙여넣으면 그 안의 제품 문의 현황 파트를 기준으로 삼는다
- 없으면 사용자에게 직전 리스트를 요청한다 (직전 리스트의 마지막 활동일·대기일이 비교 기준점)

## Step 2. Gmail 신규 활동 확인 (Gmail MCP 사용)

> 브라우저 handoff 불필요. **Gmail MCP 도구**를 쓴다 (`mcp__gmail__*`). 도구 미로드 시 ToolSearch로 로드.

1. `mcp__gmail__list_email_labels` → `OSS/BIZ contact` 라벨 ID 확인
2. 직전 리스트에 반영된 **가장 최근 날짜 이후**로 검색 (보통 직전 갱신일):
   ```
   mcp__gmail__search_emails  query: label:"OSS/BIZ contact" after:YYYY/MM/DD
   mcp__gmail__search_emails  query: subject:"Contact request" after:YYYY/MM/DD
   ```
   - `Contact request from X` = 신규 인바운드 (form 제출). 중복 제출(같은 이름·시각) 1건 처리
   - `Re: Contact request from X` = 기존 스레드 회신 (외부 발신이면 상대 회신, 우리 발신이면 우리 액션)
3. 신규·회신 메일 각각 `mcp__gmail__read_email`로 원문 확인 → 이름·이메일·직책·소속·문의 요약 추출
4. **확인 결과를 사용자에게 먼저 보고** (신규 N건, 회신 N건, 변동 없음 항목)

## Step 3. 신규 리드 점수 산정 (criteria v1.3)

신규 인바운드는 criteria v1.3 산식으로 점수 산정 (필요 시 criteria 파일 정독).

- **인입 트리아지 (v2.3 · 사전 Gate보다 우선)**: 도입/구매 의사 없이 제품 개선을 요구하는 비영업 이슈(버그·변환/출력 품질·기능 요청·GitHub Issue 번호 참조) → `개발 이슈 (파이프라인 제외)` · `[개발 이슈]`. 점수·대기일·카운트 산정 **스킵**, GitHub Issues/Discussions 라우팅. Cold와 구분(cold=식은 리드, 개발 이슈=애초에 영업 아님).
- **사전 Gate**: PDF 접근성·파싱 무관 / 학생 개인 / 정보 부족(이름+이메일뿐) → `[Cold·1차판단]` 또는 `미정`. funnel 가치 있으면 점수 모델 진입.
- **4축 (100점, cap 해제)**:
  - 축1 매출잠재력 30 (볼륨 15 + 조직규모 15)
  - 축2 네임밸류 35 (인지도 15 + 섹터대표성 10 + 규제위치 10)
  - 축3 확산력 15 (섹터파급 6 + 채널 5 + 규제연쇄 4)
  - 축4 실행 20 (실현 7 + 적극 8 + 데드라인 5)
- **컷오프**: P1 ≥70 / P2 40~69 / P3 20~39 / 미정 <20
- **자동 +1 룰**: 섹터대표성 ≥8(ODL Phase 핵심·미국 R1대학/시·주·연방) AND 총점 40~69 → P2→P1 (사유 "ODL Phase 핵심 타겟 자동 상향")
- **신규 인바운드 적극성**: 첫 인입은 응답 사이클 없음 → 상세+긴급+의사결정자면 보통 상단(6), 단답·정보부족이면 하향.
- **점수 산정 시 환각 무관용** ([[feedback_hallucination_zero_tolerance]]): 볼륨 등 미기재 항목은 추정하지 말고 "미확인" 점수 부여 + 업사이드 메모. 채널·전략 가치가 점수보다 높으면 산식 점수 + PM 검토 포인트 분리 제시 ([[feedback_pm_liability_shield]]).
- **점수 breakdown 표**는 합본 **밖**에 별도로 보여준다 (4축 + 합계 + Priority + 자동룰 적용 여부). 리포트 본문에는 등급·점수만.

## Step 4. 대기일 전 항목 재계산

- 모든 항목 "대기 N일" = (오늘 − 마지막 활동일). 직전 리스트의 대기일은 기준일이 섞여 있을 수 있으므로 **전부 오늘 기준 재계산**
- 일수 계산은 day-of-year 기준 정확히 (2026은 평년·2월 28일)
- 마지막 활동일(`날짜`)은 그대로 두고 N일만 갱신. 신규는 인입일이 마지막 활동일

## Step 5. 그룹 배치

- **신규 인바운드**(우리 첫 답변 필요)는 기본 **진행 그룹**에 편입 (2026-07-01 사용자 결정). `[신규 문의 — 첫 답변 필요]` 프리픽스 + `(우리 차례, 날짜 · 대기 N일)`
- **개발 이슈 (파이프라인 제외)**: 트리아지로 분류된 건은 진행/답변 대기/cold 어디에도 넣지 않고 **별도 `개발 이슈` 섹션**에만 표기. 헤더 카운트(전체·진행·답변 대기·cold)에서 제외. GitHub 라우팅 메모 병기
- 기존 항목 그룹은 직전 리스트 배치를 유지. 이메일 증거로 상태가 바뀐 경우만 이동하고, 이동 시 사용자에게 보고
- 룰북(`biz_contact_tracker.md`)과 그룹 배치가 충돌하면 **임의 봉합 금지·보고** ([[feedback_memory_crosscheck]])

## Step 6. 1부 출력 (고정 양식)

**반드시 코드블록**으로 출력 (불렛이 일반 렌더 시 입력 안 되는 이슈, 2026-07-01 사용자 요청). 들여쓰기·기호 그대로:

```
* [현황] 제품 문의 대응 (진행, 상시) — 전체 N건, 진행 N건, 답변 대기 N건, cold N건
* 진행 (N건)
  - 이름, [국가/B2X] 소속, 직책 — [프리픽스] 컨텍스트 요약, P?(점수) (상태, M/D · 대기 N일)
  - ...
* 답변 대기 (N건)
  - ...
* cold (N건)
  - ...
* 개발 이슈 · 파이프라인 제외 (N건)   ← 전체/진행/답변 대기/cold 카운트에 미포함
  - 이름, 소속, 직책 — [개발 이슈] 요약 (GitHub #번호 / Issues·Discussions 라우팅)
  - ...
```

양식 규칙:
- 최상위 그룹 헤더 = `* `, 항목 = `  - ` (스페이스 2칸 + 대시)
- **개발 이슈 섹션은 있을 때만 출력**하고, 헤더 `전체 N건` 및 진행/답변 대기/cold 카운트에는 포함하지 않는다 (파이프라인 밖)
- 항목 구조: `이름, [국가/B2X] 소속, 직책 — [프리픽스] 컨텍스트, P등급(점수) (상태, 마지막활동일 · 대기 N일)`
- 인명은 풀네임 ([[feedback_bm_person_name_format]]). "파트너십·마케팅" 풀네임 ([[feedback_no_pm_abbreviation]])
- 틸드 앞뒤 공백 ([[feedback_tilde_spacing]])
- 헤더 카운트는 실제 항목 수와 일치시킨다

# 2부. 한일·할일 압축 리스트

데일리 노트 여러 개를 **보고·공유용 한 덩어리 리스트**로 압축한다. ERP 공수 집계(`/suji-work-minute mbo`)와는 목적이 다르다. 이쪽은 **사람이 읽는 진행 상황 공유용**이다.

## Step 7. 구간·소스 확보

**입력 우선순위**
1. 붙여넣은 직전 주 리포트의 한일·할일 파트가 기준 (그 이후 구간만 새로 작성)
2. 없으면 이번주 월요일 ~ 오늘 구간의 데일리 노트를 읽어 작성

**소스**
- 데일리 노트 테이블 행 + `## 메모` 의 스케줄·백로그·확인 필요 블록
- 필요 시 회의록(`hand-ons/meeting_minutes/`), 1부 이메일 확인 결과 등 외부 증거로 상태 보강

## Step 8. 압축 (핵심)

이 파트의 본질은 **덜어내기**다. 데일리 노트를 그대로 옮기면 실패다.

| 규칙 | 적용 |
|------|------|
| **동종 병합** | 같은 성격 항목은 한 줄로. 예: 계약 2건 → `계약 2건 법무검토, A사·B사` / 회의 여러 건 → `검증 미팅, 팀 주간회의` |
| **단계 접기** | 한 프로젝트의 일자별 진행은 항목 1개 + 부연 1 ~ 2줄로. 일자별 행을 나열하지 않는다 |
| **잡무 삭제** | 회의록 작성, 노트 정합 정리, 리뷰 완료 등 결과물 공유 가치 없는 항목은 뺀다 |
| **미확정 묶기** | 열린 이슈는 개별 항목이 아니라 부연 한 줄에 가운뎃점으로 나열 |
| **분량 상한** | 최상위 항목 **12개 이내**. 초과하면 병합·삭제를 한 번 더 돌린다 |

## Step 9. 2부 출력 (고정 양식)

**반드시 코드블록**으로 출력한다.

```
* 항목명 (상태, 날짜)
  - 부연 1
  - 부연 2
```

- 최상위 항목 = `* `, 부연 = `  - ` (스페이스 2칸 + 대시)
- 상태 라벨: `완료` · `진행` · `예정` · `딜레이` · `대기` · `상시`
- 날짜: 단일 `8/6` 또는 구간 `8/4 ~ 8/11` 또는 마감 `~ 8/13`. 진행 중 시작만 있으면 `8/7 ~`
- 한일·할일을 **섹션으로 나누지 않는다.** 상태 라벨이 구분자 역할을 하므로 한 덩어리 리스트로 유지
- 부연은 **항목당 최대 2줄.** 그 이상은 항목이 쪼개져야 한다는 신호

# 합본

## Step 10. 교차 반영

두 파트를 그냥 나열하지 않는다. **1부 결과가 2부 리스트의 한 항목으로 압축돼 들어간다.**

```
* 비즈니스 문의 이메일 대응 (상시)
  - 신규 N건 회사명, 미회신 N건
```

- 신규 리드가 있으면 회사명까지, 없으면 `신규 없음`
- 미회신(우리 차례) 건수는 1부 진행 그룹에서 집계
- **부연 1줄 상한.** 리드 상세는 이미 1부에 있으므로 중복 금지

교차 반영 후 2부가 12개를 넘으면 압축 규칙을 한 번 더 돌린다.

## Step 11. 합본 출력

```markdown
## 제품 문의 대응 현황

​```
(1부 고정 양식 그대로)
​```

## 한일·할일

​```
(2부 압축 리스트 그대로)
​```
```

- 두 파트 모두 **각각 코드블록**. 하나로 합치지 않는다 (복사 단위가 다름)
- 섹션 제목은 위 2개 고정. 임의로 바꾸지 않는다

## Step 12. 부속 정보 (코드블록 밖, 맨 아래 한 번만)

순서 고정:

1. **신규 리드 점수 breakdown** — 있을 때만, 4축 표
2. **변경 요약** — ➕ 신규 N건(점수·등급) · 🔄 대기일 오늘 기준 재계산 · 카운트 변화(예: 30 → 31건) · 취합·삭제한 항목 한 줄
3. **확인 필요 · 플래그** — ⚠️ 노트 간 상태 충돌 · 미확정 일정 · 기한 도래 · 근거 부족 항목

## 규칙

- **직전 리포트 = SoT.** 라벨·그룹·흐름 임의 변경 금지. 변경은 이메일·노트 증거 기반 + 보고
- **데일리 노트에 없는 작업을 추론으로 만들어내지 않는다**
- **변경 전 확인은 점수·그룹 신설 등 판단이 필요한 경우만.** 단순 대기일 재계산·신규 반영은 보고 후 출력
- **노트 간 상태 충돌은 임의 봉합 금지·보고** ([[feedback_memory_crosscheck]])
- **근거 없는 수치·일정 단정 금지.** 미확인은 `확인 필요`로 분리 ([[feedback_hallucination_zero_tolerance]])
- **파일 쓰기는 사용자 확인.** 기본은 출력만. 사용자가 "파일 반영"을 요청하면 위치 확인 후 작성
- **PII 안내**: 외부 담당자 이름·이메일 포함 시 응답 말미 1줄 안내 (조직 정책)
- 엠대시(`—`) 사용 금지. 라벨은 콜론, 나열은 가운뎃점. 단 1부 고정 양식의 구분 기호는 기존 양식 유지
- 틸드는 앞뒤 공백 (`8/4 ~ 8/11`), 경로 틸드는 예외
- 부분 실행(`biz` / `tasks`)일 때는 Step 10 교차 반영을 건너뛴다
